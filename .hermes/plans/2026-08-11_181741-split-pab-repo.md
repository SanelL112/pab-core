# Personal-Assistant-Bot Repo Decluttering & Division Plan

> **For Hermes:** This is a refactor/reorg plan, not greenfield code. "TDD" here means: the existing test suite (`pytest`) + `bot.service` starting cleanly are the regression gate run after every task. Execute task-by-task; do not batch moves.

**Goal:** Divide the cluttered `~/personal-assistant-bot` monorepo into clear parts — separating *source* from *generated artifacts* from *dead cruft* — and reorganize the 25 flat root modules into a proper `src/pab/` package with named subpackages, without breaking the live bot, the 4 systemd units, or the shared-`.git` `-release/` worktree.

**Architecture:** One repo, three-layer separation. (1) Purge generated data + dead files from git tracking (biggest declutter, ~144 files leave the index, disk untouched). (2) Regroup remaining ~40 source modules into `src/pab/{core,ai,ingest,study,bot,ops}` subpackages behind a single `pab` import root. (3) *Optional, gated* Phase 3: extract cleanly-decoupled subsystems into separate git repos once package boundaries are proven. We recommend stopping after Phase 2 unless separate repos are explicitly wanted — see Open Questions.

**Tech Stack:** Python 3, python-telegram-bot, httpx/requests, pytest, systemd (user is on Linux, sudo NOT passwordless), git worktrees.

## Phase 2 — Restructure flat modules into `src/pab/` subpackages

**Principle:** Move files with `git mv` (preserves history), add a shim so old import paths keep working during transition, update imports package-by-package, run tests after EACH package. `config` stays importable — we re-export it.

### Task 2.1: Scaffold the package tree
**Objective:** Create the target layout with `__init__.py` files.
**Files:** Create `src/pab/__init__.py`, `src/pab/{core,ai,ingest,study,bot,ops}/__init__.py`, `pyproject.toml` (editable install).

```bash
cd ~/personal-assistant-bot
mkdir -p src/pab/{core,ai,ingest,study}
for d in "" core ai ingest study; do touch "src/pab/$d/__init__.py"; done
```
Create `pyproject.toml` (so `pab` is importable via `pip install -e .`, replacing sys.path hacks):
```toml
[build-system]
requires = ["setuptools>=68"]
build-backend = "setuptools.build_meta"

[project]
name = "pab"
version = "0.1.0"
requires-python = ">=3.10"
dynamic = ["dependencies"]

[tool.setuptools.packages.find]
where = ["src"]

[tool.setuptools.dynamic]
dependencies = {file = ["requirements.txt"]}
```
Then: `pip install -e .` and verify `python -c "import pab; print(pab.__file__)"`.

### Task 2.2: Move `core` modules first (config is the keystone)
**Objective:** Establish `pab.core.config` as the canonical config path with a back-compat shim.
**Files:** `git mv config.py src/pab/core/config.py` (+ utils, activity_log, telegram_logger, send_telegram, inline_keyboards, voice_handler).

Steps:
1. `git mv config.py src/pab/core/config.py` (repeat for the 7 core modules).
2. Add root shim `config.py` (NEW, temporary) so the ~35 existing importers don't break yet:
   ```python
   # config.py — transitional shim; import from pab.core.config
   from pab.core.config import *  # noqa
   from pab.core.config import STATE_FILE, PAB_CONFIG_DIR  # explicit re-exports if * misses them
   ```
   (Repeat a one-line shim for each moved core module: `from pab.core.utils import *`.)
3. Run: `pytest -q tests/test_p0_security.py tests/test_reliability.py -q` — expected: same as baseline.
4. Commit: `git commit -am "refactor(core): move config/utils/etc to pab.core with shims"`.

> **Pitfall:** `from x import *` misses names not in `__all__` and misses submodule attributes accessed as `config.SOMETHING`. Grep `grep -rhoE 'config\.[A-Za-z_]+' src tests | sort -u` and ensure each is re-exported. Sanel rejects guessed constants — enumerate them, don't assume `*` covers it.

## Phase 3 — OPTIONAL, GATED: extract subsystems into separate git repos

Only if Sanel explicitly wants *multiple repositories* (not just packages). Candidates with the cleanest boundaries: **`ops/`** (infra/systemd/cluster — zero Python coupling to the bot) and **`study/` engine** (depends only on `core.config` + `ingest`). `core`, `ai`, `bot`, `ingest` are too tightly coupled via `config`/`utils` to separate without a published shared package.

Per subsystem, when extracted:
1. `git subtree split -P ops -b split-ops` (preserves that path's history) → push branch to a new repo.
2. Or `git filter-repo --path ops/` on a **fresh clone** (NEVER on the live repo — it shares `.git` with the `-release/` worktree and would desync it).
3. Re-consume via `pip install -e` from the new repo or a git submodule.

> **Blocking risk:** history rewrite on the primary `.git` breaks the `-release/` worktree. Any filter-repo MUST run on an isolated clone. Flag to Sanel before doing this.

## Risks, Tradeoffs, Open Questions

**Risks**
1. **Shared-`.git` worktree** (`-release/`): any history rewrite desyncs it. Phase 1 & 2 use `git rm --cached`/`git mv` only (no rewrite) — safe. Phase 3 filter-repo MUST run on an isolated clone.
2. **4 systemd units pinned to the repo path** — moving the entrypoint requires the drop-in in Task 2.8; verify `canvas-browser`, `pab-dashboard-agent`, `assignment-caldav` still resolve their working dirs (they point at the repo root, which is unchanged — only the *entrypoint script path* moves).
3. **`from x import *` shims** can silently drop names — enumerate every `config.NAME` reference and re-export explicitly (Sanel rejects guessed coverage).
4. **`!`-prefix / handed-off sudo commands may silently no-op** — always re-verify live `systemctl show`/`journalctl` after Task 2.8, never assume it ran.
5. **`.git` stays 498M** even after untracking — the bloat is in *history*. Only a Phase-3-style filter-repo on a clone reclaims it. Decide whether that's worth the worktree risk.

**Tradeoffs**
- Package restructure (Phase 2) vs. separate repos (Phase 3): packages give clean boundaries + one-checkout ops with near-zero risk; separate repos give hard isolation but multiply CI/deploy/worktree overhead for a single-maintainer project.

**Open Questions (need Sanel's call before Phase 3, not before Phase 1):**
1. **"Multiple parts" = subpackages in one repo (recommended, Phase 2) or genuinely separate git repos (Phase 3)?**
2. Reclaim the 498M `.git` via history rewrite on an isolated clone (accepting a `-release/` worktree re-setup), or leave history intact?
3. Keep `CODEBASE_ANALYSIS.md` / `README.md` in root, or also move analysis docs to `docs/`?
